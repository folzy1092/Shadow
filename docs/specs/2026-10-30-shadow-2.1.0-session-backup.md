# Shadow 2.1.0: бэкап аккаунтов в связке ключей (спек, 2026-10-30)

Статус (2026-10-30): **сделан минимум (решение 7.9)**, остальное — раздел 9.
Версия: новая функция, значит 2.1.0 (средняя цифра), не 2.0.x.

## 1. Зачем

Удалил Shadow, поставил заново, нажал одну кнопку и получил все свои аккаунты
обратно, без номера, SMS и облачного пароля.

Это **не** защита от потери номера или телефона. Бэкап хранит существующую сессию.
Если сессию завершили в «Активных сеансах» или она истекла по сроку неактивности
(«Если не в сети…»), бэкап бесполезен, и входить придётся по номеру. Это нужно прямо
написать в описании функции.

## 2. Как это сделано в Swiftgram (проверено по их репо 2026-10-30)

- `Swiftgram/SGKeychainBackupManager`: обёртка над `SecItem*`, `kSecClassGenericPassword`,
  сервис `<bundleId>.sessionsbackup`, одна запись на аккаунт (account = peerId),
  `kSecAttrAccessibleWhenUnlocked`, без `Synchronizable`.
- `Swiftgram/SGProUI/Sources/SessionBackupController.swift`: в запись кладётся
  JSON-обёртка `SessionBackup { name, date, accountRecord }`, где `accountRecord` —
  целиком `AccountRecord<TelegramAccountManagerTypes.Attribute>` с атрибутом
  `.backupData` (`AccountBackupData`: peerId, главный DC, auth key и т. п.).
- Восстановление: для каждой записи, если аккаунта с таким peerId ещё нет,
  `accountManager.transaction { createRecord(attributes) }`, где `sortOrder` заменён
  на следующий. Telegram поднимает аккаунт со старым ключом, и сервер видит ту же
  сессию.
- Минусы у них: экран только в Pro-настройках, то есть сначала нужно войти хоть
  в один аккаунт. Бэкап делается только по кнопке. Восстановление без Face ID.

## 3. Что делаем в Shadow

### 3.1 Хранение (TelegramCore, новый файл `AyuGram/ShadowSessionBackup.swift`)
- Связка ключей: `kSecClassGenericPassword`, сервис `<bundleId>.shadow.sessions`,
  account = `String(peerId)`.
- Данные: JSON `{ v: 1, name, username, date, record }`, где `record` — `AccountRecord`
  (он `Codable`). Брать только записи без `.loggedOut`, с ненулевым `backupData.peerId`
  и только `.production` (тестовое окружение пропускать).
- Доступ: см. решение 7.1. По умолчанию
  `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, без `kSecAttrSynchronizable`.
- Face ID: см. решение 7.2. Если да, у записи `SecAccessControl` с `.userPresence`
  (Face ID / Touch ID / код телефона). Тогда чтение показывает системный запрос
  само, свой UI не нужен. Список имён для экрана восстановления хранить **отдельной**
  записью без access control (только имена, @username и даты, без ключей), чтобы
  показать список до запроса Face ID.
- Чистая часть (кодирование и разбор записи, фильтр «что бэкапить», слияние) —
  в Foundation-only файле `ShadowSessionBackupModel.swift` с тестами
  `Tests/ShadowSettings/SessionBackupTests.swift` (в `build-system/ci/test_shadow_foundation.py`).
  Сама работа со связкой ключей — в отдельном файле, без тестов на Linux.

### 3.2 Когда бэкапить (автоматически)
- Подписка на `accountManager.accountRecords()` (как `backupSessionsFromView` у
  Swiftgram), где-то рядом с менеджером аккаунтов в `SharedAccountContext`. При
  каждом изменении:
  - новые и изменённые аккаунты записать;
  - аккаунты, ставшие `.loggedOut` или удалённые, **стереть из связки** (выход из
    аккаунта должен убивать бэкап, иначе в списке останется мёртвая запись);
  - имя и @username брать из `activeAccountsWithInfo`.
- Тумблер «Бэкап аккаунтов» (по умолчанию: решение 7.4). Выключение стирает все записи.
  Поскольку это настройка устройства, а не аккаунта, держать её в UserDefaults
  (как Spaces/Duress), **не** в `AyuGramSettings` (те привязаны к аккаунту и
  синхронизируются между аккаунтами).

### 3.3 Восстановление
- **Экран входа** (`AuthorizationUI`, `AuthorizationSequencePhoneEntryController` /
  `...SplashController`): если в связке есть записи, показать кнопку «Восстановить
  аккаунты (N)». Это главное отличие от Swiftgram: после переустановки номер не нужен
  совсем.
- **В настройках:** Shadow → Аккаунты (или Хранилище Shadow) → «Бэкап аккаунтов»:
  тумблер, список (имя, @username, дата, «в приложении / нет»), «Восстановить»,
  «Удалить из бэкапа» (по одному и все).
- Логика восстановления как у Swiftgram: пропустить peerId, которые уже есть,
  `createRecord` со свежим `sortOrder`. После этого переключиться на первый
  восстановленный аккаунт.
- Если сервер ответил на восстановленный аккаунт 401 (сессия мертва), аккаунт
  уходит в обычный выход Telegram. Тогда запись из связки стереть и показать «Сессия
  @name больше недействительна, войди по номеру».

### 3.4 Защитные функции Shadow
- **Тревожный код (`ShadowDuress`)** с выходом из выбранных аккаунтов: стирать их записи
  из связки в том же действии. Иначе после выхода под принуждением аккаунт можно
  поднять из бэкапа (если сервер ещё не убил ключ; logOut ключ убивает, но запись
  всё равно должна исчезнуть).
- **Паник-жест** с выходом — то же.
- **Пока активна тревожная сессия** (`ShadowDisguise.isDuressActive`): экран бэкапа
  и кнопка восстановления скрыты.
- **Второе пространство** работает по чатам, а не по аккаунтам, поэтому на бэкап не влияет.
- **Маскировка (`ShadowDisguise`)**: кнопку на экране входа показывать только если
  маскировка не активна (проверить, как она выглядит на экране входа).

## 4. Риски и что проверить до кода

1. **Подпись и Team ID.** Записи связки ключей видны только приложению с тем же
   префиксом идентификатора (Team ID). Нужно проверить, как ставится Shadow
   (самообновление с подписью на устройстве, §5g карты; Sideloadly и т. п.). Если
   при переустановке меняется сертификат или Apple ID, бэкап недоступен. Найти
   entitlements (`keychain-access-groups`) в сборке и описать в карте.
2. **Переживает ли связка удаление приложения.** Сейчас на iOS — да (Apple так и
   не включила очистку при удалении). Проверить на устройстве: сделать бэкап, удалить
   Shadow, поставить, увидеть кнопку.
3. **Две копии одной сессии.** Если тот же ключ поднят на двух устройствах сразу
   (через бэкап iPhone или iCloud), сервер может сбрасывать сессию. Поэтому по
   умолчанию ThisDeviceOnly.
4. **Формат `AccountRecord`** может поменяться в апстриме. Хранить версию `v` и
   при неудаче разбора не падать, а показывать «запись не читается».
5. **Безопасность.** Кто знает код телефона, тот поднимет аккаунты. С Face ID
   (`.userPresence`) это равно разблокировке телефона, не хуже самого Telegram без
   код-пароля.

## 7. Решения Folzy (2026-10-30)

1. **Хранение:** только на телефоне, без iCloud Keychain, **но с переносом через
   зашифрованный бэкап iPhone**: `kSecAttrAccessibleWhenUnlocked` (не ThisDeviceOnly),
   без `kSecAttrSynchronizable`.
2. **Face ID / код телефона перед восстановлением:** да (`SecAccessControl` `.userPresence`).
3. **Одна кнопка «Восстановить аккаунты (N)»** импортирует **все** аккаунты из связки
   сразу, без выбора по одному.
4. **Сессии на сервере не трогаем** (остаются живыми).
5. **Ошибки:** если аккаунт не восстановился (сессию завершили или любая другая
   ошибка), показать текст ошибки по каждому аккаунту и кнопку «Скопировать», чтобы
   Folzy переслал текст агенту.
6. **Подпись:** у каждого пользователя свой сертификат; бэкап работает, пока
   переустанавливаешь со своей подписью. Написать это в описании функции.
7. **Тревожный режим / второе пространство:** по желанию агента, если дёшево. Минимум:
   выход из аккаунта (в т. ч. тревожным кодом) стирает его запись автоматически
   (через синхронизацию с `accountRecords`, раздел 3.2). Скрытие экрана в тревожной
   сессии — отложено, если не хватит ресурса.
8. **Тумблер по умолчанию:** вкл (решение агента, Folzy не возражал).
9. **Объём:** если ресурса мало, делать минимум (хранение, автобэкап, кнопка
   восстановления с Face ID и ошибками); остальное (экран управления, ссылки, поиск)
   оставить в спеке на потом.

## 8. План работ (порядок, чтобы можно было прерваться)

1. `ShadowSessionBackupModel.swift` + Foundation-тест (чистая логика). Коммит.
2. `ShadowSessionBackup.swift` (связка ключей) + автобэкап из `accountRecords()`. Коммит.
3. Экран в настройках (список, восстановить, удалить, тумблер) + поиск + ссылка. Коммит.
4. Кнопка на экране входа. Коммит.
5. Duress / паник: стирание записей; скрытие в тревожной сессии. Коммит.
6. Контрактные тесты, карта, notes, версия 2.1.0. Коммит.
7. Один push, зелёный CI, объявление (§5d). Проверка на устройстве: бэкап → удалить
   приложение → поставить → кнопка → аккаунты на месте.

Каждый шаг — отдельный коммит, локально; push один раз в конце (правило «одна сборка —
несколько фич»). Если работа прервётся, следующий агент продолжает с первого
невыполненного пункта: пункты сверять по `git log`.
